# 페이지 상단 긴 표와 앵커 뒤 본문의 겹침 수정

기준은 첫 fragment fit 수정 5d90870a839ebbe07b087426d3305854ae0db15b이며, 앞선 f2423db182555d7a73cf06974fbcfeb19067cd96와 5d90870 브랜치의 공개 HEAD는 변경하지 않았다. 후속 dev/table-trailing-host-flow에서 소스·검증만 추가했다.

## 재현과 배치 근거

48행 반복 머리행 표의 앵커 문단에 있는 `본문 보존`이 편집 전부터 첫 머리행과 겹쳤다. 기준 엔진의 실제 Mac Electron에서 첫 표 조각과 본문 줄의 시작은 모두 y=132.3px였다. 표는 11페이지에 걸쳐 있지만 앵커 문단 본문은 첫 페이지에 그려졌다. 첫 fragment fit이나 과거 redo의 새 결함으로 보고하지 않았다.

합성 HWPX 소스는 표 run 뒤에 본문 run을 저장한다. 표는 글자처럼 취급하지 않으며, 겹침을 허용하지 않는 TopAndBottom·Page·Top·offset=0·RowBreak이다. 문단에 표시되는 표 앞 텍스트는 없다. [한컴 안내서](https://cdn.hancom.com/link/docs/HanwordUserGuide%28ipad%29KO.pdf)의 자리 차지 설명은 개체 영역에 본문이 들어가지 않는 근거다. 본문을 마지막 표 조각 뒤로 보낸 판단은 이 설명과 해당 소스의 앵커·텍스트 순서를 함께 해석한 것이며, 실제 한컴 앱 배치와 대조한 결과는 아니다.

기존 partial table layout은 앵커 문단을 먼저 렌더링하고 그 결과의 종료 높이를 쓰지 않은 채 같은 y에서 표를 렌더링했다. 모델 문자열·스타일은 보존됐어도 물리 배치가 겹쳤다.

## 변경

단일 단, 표 각주 없음, 단일 RowBreak 표, 문단 텍스트 시작 전에 앵커, Page·Top·offset=0·TopAndBottom·겹침 불허 조건의 continuation 경로에서 앵커 뒤 본문을 별도 PartialParagraph 항목으로 배치한다. 마지막 표 조각 후 실제 줄 높이와 문단 줄 간격으로 남은 공간을 검사하고, 첫 줄이 맞지 않으면 새 페이지로 넘기며 여러 줄은 페이지별로 분할한다. 후행 일반 문단도 소비된 본문 높이 뒤에서 이어진다.

기존 pre_emitted_host_paras 소유권으로 표 조각 내부의 본문 복사본을 억제한다. 문자열·원본 위치 속성·셀 속성·clip·페이지 경계 진단을 바꾸거나 임의 안전 간격을 넣지 않았다. 기존 마지막 fragment의 spacing_after는 별도 본문 항목에서 한 번만 소비한다. 문서명·48행·특정 좌표를 구현 조건으로 쓰지 않는다.

짧은 본문은 마지막 표 조각 페이지에서 실제 표 테두리 y=599.5467px 뒤의 줄에서 시작한다(공개 위치 API의 0.1px 반올림 y=599.5). 긴 본문은 표 페이지 0–10 뒤의 페이지 10–14에 걸쳐 이어진다. 용지 아래 여백을 20252 HWPUNIT로 설정한 별도 합성 사례는 마지막 테두리 783.0667px, 본문 하단 795.76px이어서 13.3px 본문 줄을 다음 페이지로 넘긴다. 표 마지막 페이지 14, 본문 시작 15다. 양형식 첫 로드에서 이 새 페이지 경계를 직접 확인한다.

## 검증

최종 Mac Electron 44.3.0의 56개 경우, undo/redo 100쌍, 실제 HWP/HWPX 호스트 저장·재열기 100회를 통과했다. 초기 10개 입력 문서와 편집 직후/재열기 150회의 합계 160회·1226페이지를 측정했다. 최대 테두리 하단은 본문 안 0.28px, 글자 하단은 안 2.63px였고 수직 clip으로 숨겨지거나 1px 이상 잘린 글자는 0이다. renderer 오류 0, 정상 앱 종료 0이다. 같은 실제 저장 바이트 100개를 새 Native 엔진에서도 전체 SVG·페이지 수·본문/셀 문단/문자 스타일 ID·표/용지 속성으로 독립 비교해 모두 통과했고 LAYOUT_OVERFLOW 진단은 0이다. Node 문법 검사, TypeScript 검사와 git diff --check도 통과했다. 새 WASM SHA는 4d020a603b18ca3ce248a5014463ee581762c798e27225d5e14e9457835b6e23이며 Electron이 받은 바이트 SHA도 일치한다. 수치와 해시는 동반 proof.json에 기록한다. 실제 Mac Electron의 첫·중간·끝 조각 입력, 단일/전체 치환, 높이 증가·감소, 크기 무변경, 본문 입력을 HWP/HWPX 입력에 적용했다. 긴 본문과 terminal budget 부족 사례에는 본문 입력과 단일 치환을 적용했다. 제품의 deferred pagination idle을 기다리고 실제 키보드·대화상자·undo/redo·호스트 저장 IPC·파일 재열기를 사용했다. 파일 선택 응답과 전용 프로필은 QA에서 제어했다.

본문·셀의 모든 문단 속성과 문자 스타일 ID, 페이지 정의와 표 배치 속성, 전체 SVG·페이지 수·저장 바이트 SHA를 비교한다. 셀별 렌더링 문자열을 물리 조각 순서대로 모아 원문과 비교해 페이지 경계에서 식별 문자열이 잘리는 경우도 검사한다. 반복 머리행은 각 조각의 전체 문자열을 비교한다. 원시/가시 비공백 스칼라 소유권, 후행 AFTER_TABLE_END의 단일 소유권도 확인한다. 실제 Electron 글꼴의 SVG bbox와 수직 clip은 기존 엔진과 같은 2px 본문 경계 허용치로 검사한다.

별도 차등 검증은 겹침 허용·문단 기준·양수 Page offset·앵커 앞 표시 텍스트의 양형식 8건에서 기준/신규 엔진 전체 SVG가 동일함을 확인한다. 적용 대상 양형식 2건에서는 SVG 차이를 확인해 검증의 감도를 확인한다.

첫 전체 QA는 본문이 비어 있는 번호 목록에도 본문을 요구해 중단됐고, 다음 QA는 페이지 경계 사이에 반복 머리행이 삽입되는 식별 문자열을 연속 토큰으로 요구해 중단됐다. 조건과 셀별 조각 소유권 검사를 수정한 뒤 새 디렉터리에서 전체 검증을 실행했다. 이전 실패·중간 결과는 모두 보존했다. 안쪽 여백 문서의 반복 거절 증거 설명도 첫 거절의 전체 모델/양형식 export 검사와 반복 거절의 history/dirty 검사로 정확히 구분했다.

## 보존·범위·다음 후보

../table-trailing-host-flow-qa에 baseline, targeted-2, long-target, budget-target, 최종 실제/Native 검증, scope 및 빌드 증거를 보존한다. 기존 source-owned 캐시 산출물은 cache-checkpoint로 이동해 보존했다. target 한도 4.48GiB와 가용 공간 최소 15GiB를 감시했고, Native peak 4,795,482,112bytes, Native checker rebuild peak 4,800,872,448bytes, WASM peak 4,763,385,856bytes로 모두 4,810,363,371bytes 한도 이내였다. 기존 Electron·오프라인 Rust·기존 UI 자산 16개를 재사용했다. 바이너리·개인 원본·QA 저장 파일·대용량 캐시는 커밋하지 않는다. 영구 삭제·설치·중복 패키징·병합·릴리스는 하지 않았다.

이번 수정은 continuation 경로의 좁은 배치 수정이다. 한 페이지에 표 전체가 수용되는 선행 경로, 합쳐진 셀·중첩 표·실제 부분 저장 프레임·누락/0높이 저장 frame·각주·다단·비기본 문단 앞간격의 독립 검증은 수행하지 않았다. 수직 경계/clip 검증이며 가로·raster 픽셀·OS 선택창·물리 IME·수동 GUI·Linux·한컴 교차검증을 대신하지 않는다. 전체 Rust lib test는 기존 누락 fixture 때문에 실행하지 않고 Native example과 실제 Electron을 사용했다. 모든 문서의 overflow나 모든 개체 배치가 해결됐다고 주장하지 않는다.

다음 좁은 구현 후보는 표 전체가 한 페이지에 수용되는 경로에서 앵커 뒤 본문과 표의 배치·문단 간격을 같은 기준으로 재현하는 것이다. 이어 실제 부분 저장 프레임과 합쳐진 셀의 수직 경계를 별도 사례로 검증한다.
