# 투명 채우기 의미·편집·재저장 검증

4784d14의 미해결 템플릿 조회 차이는 읽기 자체에서는 같은 그림을 가리키지만, 편집으로 이어지면 실제 결함이었다. 보존된 엔진/원래 UI patch builder와 작은 합성 문서에서 재현했다. 파란 쪽 배경(#d0e8ff) 위의 투명 셀·도형이 채우기를 바꾸지 않은 확인 동작으로 흰색을 덧칠했다. 도형에 none을 지정해도 잔여 흰 단색 데이터가 남아 HWPX 재열기에서 단색으로 돌아왔다. 채우기만 바꿀 때 셀 테두리/대각선이 새 기본값으로 바뀌는 문제도 확인했다.

## 단계별 원인과 수정

- HWP 템플릿의 테두리/배경은 `Solid + background_color=0xFFFFFFFF + pattern_type=-1`이다. HWPX header 파서는 faceColor=none을 `None + solid payload`로 읽는다. 이 두 저장 표현은 무늬가 없는 경우 모두 무채움이다. 실제 흰색은 상위 바이트가 0인 0x00FFFFFF다. 본문 도형 HWPX는 Solid 태그를 유지하는 경우도 있다.
- 렌더러는 이미 상위 바이트가 있는 무무늬 단색을 그리지 않는다. 기존 getter는 fillType=solid와 RGB #ffffff를 반환해 이 의미를 잃었다. 공통 Fill.effective_type()을 조회에 사용해 글자/문단/셀/표/쪽/도형의 값이 렌더링 의미를 따르게 했다. 원시 모델을 조회 중에 변경하지 않는다. 무늬가 있는 채우기와 진짜 흰색은 solid로 유지한다.
- 도형 속성의 none은 모든 채우기 하위 필드를 처리한 뒤 잔여 단색·그라데이션·이미지 데이터를 지운다. 숨은 컨트롤 값이 같이 전달돼도 None이 우선한다. 다른 속성의 변경은 기존 브러시를 보존한다.
- 실제 도형 UI patch builder는 RGB 픽커 표시값이 그대로면 원래 COLORREF를 보존한다. none에서 solid를 선택하면 실제 RGB 흰색 등을 명시적으로 전달한다. 패턴 없는 0/-1 표현 차이 때문에 브러시를 다시 쓰지 않는다.
- HWPX의 비어 있는 winBrush(None+solid)는 HWP의 투명 Solid 레코드로 저장해 숨은 색·무늬·알파 데이터를 보존한다. HWP 태그와 HWPX 태그를 무리하게 동일화하지 않았다.
- 셀/표의 부분 채우기 변경은 현재 BorderFill을 기준으로 합쳐 지정하지 않은 테두리·대각선을 보존한다. 자원 없는 0번 셀의 무테두리도 보존한다. 0번을 거절하던 undo ID API의 범위 검사는 그대로이며 거절 시 모델 무변경을 확인했다.

렌더러 제품 코드는 변경하지 않았다. 보존된 42개 저장 파일을 구/신 엔진에서 동일 바이트로 읽었을 때 전체 SVG는 모두 같고 getter만 4파일에서 달랐다. 이미 흰색으로 잘못 저장된 파일을 임의로 투명으로 바꾸지 않는다. 기존의 유효한 흰색 입력은 그대로 흰색이다.

## 완료 검사

- 수정 전 보존 엔진: 7상태, 저장 42파일, 재열기 210회, snapshot undo/redo 7회. 원인·원래 UI 소스·원시 SVG·실패 시도를 별도 QA에 보관했다.
- 최종 WASM: 템플릿 글자/문단, 투명 셀·도형, 실제 흰 셀·도형, 패턴 도형, 명시적 none 도형, 표 채우기 등 8상태. 각 initial/white/none 단계에서 HWP/HWPX 두 방향의 3회 저장 사슬을 검사했다. 48파일, 재열기 240회, undo/redo 8회, 이슈 0. 변경 없는 확인에서 전체 SVG와 채우기가 유지되고, 부분 셀/표 변경에서 테두리·대각선이 유지됐다. 실제 도형 UI patch builder를 실행했고 셀/표 배경 분기는 소스의 로직을 API로 검사했다.
- Native: 최종 48파일의 전체 SVG·getter가 동일 바이트의 WASM과 정확히 일치. 재저장/재열기 96회에서 원시 단색 payload와 알파까지 일치했다(투명 도형 알파 97 포함). 모델 조회·저장은 원본 모델을 변경하지 않았다.
- 기존 새 문서 6상태/36파일/60회 WASM 사슬 및 Native 6상태/60회 사슬을 다시 확인했다. 기존 템플릿 getter 예외는 0개이며 Native 비교에서 이전 예외 처리를 제거했다. 저장 회귀 결과 11파일을 더한 47파일/94회 Native 재저장도 통과했다. 현재 결과 95파일/190회 Native 재저장과 별도로 기존 샘플 42파일/84회 모델 진단을 완료했다.
- 저장 회귀 19묶음, 정식 회귀 18개, Native standalone 단위 검사 2개, TypeScript noEmit, Clippy lib/두 example -D warnings 모두 최종 코드에서 통과했다. 기존 표·스타일 삭제·전파의 기본 회귀를 포함한다. 미등록 char ID 42 및 이전 실패 샘플의 누락 ID 0 거절·무변경도 유지됐다.
- HWPX 48파일의 서식 참조 3,763개가 실제 header 정의와 일치했다. 상속 글꼴 sentinel 390개를 별도 집계했으며 일반 미등록 참조를 허용하지 않았다.

## 보존과 한계

QA 루트는 `../transparent-fill-qa`다. final-pkg, Native 바이너리 두 개, final-verified manifest, 모델/브러시 기록, 원시 SVG, 실패 시도·보호 해시·예산 로그를 보관했다. 기존 캐시 백업 515개를 읽기 전용으로 재사용하고 필요한 항목만 추가 백업했다. 변경된 기존 캐시 14개를 복원한 뒤 38,857개 보호 파일의 변경·누락 0을 확인했다. 복원 후 보관 Native 바이너리에서도 95파일/190회 검사를 재실행해 통과했다.

새 target 루트·앱/ZIP·푸시/릴리스·산출물 삭제는 없다. dev12 strict 서명은 유효하고 기존 앱·문서·권한·클립보드는 보존했다. 이 작업에서 GUI 창이나 OS 대화상자는 만들지 않았다. 실제 Mac GUI/서명된 현재 앱의 통합 검사는 하지 않았으며, Node에서 UI 순수 함수와 엔진/API를 검사한 결과다. 물리 IME·클립보드·다른 플랫폼 실행·모든 패턴/이미지/그라데이션의 픽셀 해석은 검증 범위 밖이다. 전체 Rust lib 단위 검사의 기존 누락 fixture 3개는 그대로 두고 standalone 검사로 진행했다.

다음 확인 항목은 공간 예산 내 승인된 현재 앱 후보에서 속성 대화상자의 실제 확인/취소·undo/redo 및 OS 파일 저장을 검사하는 것이다. 마지막 공간 수치와 전 실행의 최대 target/최저 실제 여유는 proof.json에 기록했다(기준 target 4.5GiB 이하, 실제 여유 15GiB 이상).
