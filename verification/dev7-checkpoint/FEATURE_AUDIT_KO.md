## 다음 한 가지: 일반 본문의 기존 문단 번호 목록 이어 쓰기

보고서에서 번호 1·2의 목록 뒤에 설명 문단을 넣고 목록을 3번으로 이어 가는 기본 작성 경로다. 현재 대화상자의 두 이어쓰기 선택은 기존 번호 정의를 정확히 찾아 재사용하지 못한다.

패키지 엔진과 실제 `NumberingDialog.onConfirm`, `format:para-num-shape`, `InputHandler.applyNumbering`/`executeOperation`, `CommandHistory`로 다음을 재현했다. Modal DOM·커서/refresh는 adapter다.

| 재현 | 기대 | 관측 |
|---|---|---|
| 기존1·2 목록 → 설명 문단 → 번호 없는 다음 항목, ‘앞 번호 목록에 이어’ | 기존 numberingId1, SVG ‘3.’ | 신규 id2, SVG ‘1.’, 조회 restartMode2 |
| 이미 같은 id1 목록의 세 번째 항목에서 ‘이전 번호 목록에 이어’ | id1 유지, SVG ‘3.’ | 신규 id2, SVG ‘1.’, 조회 restartMode2 |
| 이미 같은 목록에서 ‘앞 번호 이어’ 대조 | SVG ‘3.’ | ‘3.’ |
| 새 목록을5번으로 시작하는 표시 대조 | SVG ‘5.’ | ‘5.’ |
| 두 실패 사례에 기존 id1을 실제 applyNumbering API로 적용 | SVG ‘3.’ | 둘 다 ‘3.’ |

실패2건/정상 대조4건을 확인했다. HWP/HWPX 재열기8건에도 같은 번호 정의와 잘못된/정상 SVG 표시가 유지된다. SVG 글리프의 이어진 텍스트에서 대상 항목 직전 번호를 검사했으며 눈으로 화면을 읽은 결과가 아니다. 본문 문자열과 이웃 문단 속성은 보존됐다.

원인 근거는 `numbering-dialog.ts:426`의 매 확인 시 새 정의 생성, `format.ts:366`의 ‘앞 번호’ 분기에서 이전 문단이 아닌 현재 문단 번호 ID만 사용, `format.ts:375`의 ‘이전 번호’ 분기에서 신규 ID 적용이다. 이미 존재하는 번호 ID를 쓰는 엔진 API는 정상 표시한다. 또 새 정의를 이력 밖에서 생성해 undo 뒤에도 정의 수가1→2로 남고 HWPX 바이트는 원복되지 않는 것을 관측했다. 이 문제는 같은 이어쓰기 연결을 고칠 때 정의/참조의 원자적 이력 범위에 포함해야 한다.

후속 범위는 지원 일반 본문에서 기존 번호 정의와 목록 순서를 찾아 ‘앞/이전 목록에 이어’의 대화상자 선택을 정확히 적용하는 것이다. 캐럿·지원 선택 범위와 번호 수준, 끼어 있는 비번호 문단을 다루되 새 목록 시작의 기존 표시 대조군을 보존한다. 텍스트/직접 서식·이웃 목록/스타일·번호 정의/문서 참조를 보존하고 유효하지 않은 대상을 무변경 거절하며 undo/redo·HWP/HWPX 재열기로 검증한다. 중첩 셀·각주 번호 확장을 이 본문 누락과 섞지 않는다.
