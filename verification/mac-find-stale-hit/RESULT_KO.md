# Mac 찾기·바꾸기의 오래된 검색 위치 방지

찾기·바꾸기 창을 열어 둔 채 검색어·대소문자 옵션을 바꾸거나, 본문을 편집하거나, 다른 문서를 열면 이전 검색 좌표로 치환하는 결함을 수정했다. 기존 main `eb501dc8d4adf2fbd79c329834e457b77ad5740f`의 실제 Mac Electron에서 다섯 경우를 재현했다. 본문 앞에 `XYZ`를 넣은 뒤 바꾸기는 `XYZAPRE needle …`를 `XYZAPQdle …`로 손상했고, 다른 문서를 연 뒤에는 `OTHER safe content🙂`의 이전 좌표를 치환했다. 검색어가 없거나 빈 검색어여도 이전 결과를 바꿨다.

FindDialog가 검색 결과와 함께 검색어·대소문자·문서 세대를 기억한다. 입력과 옵션 변경, document-mutated·document-changed·history-jumped에서 결과를 무효화하며 창을 닫을 때 구독을 해제한다. 바꾸기 직전에도 검색 조건과 문서 세대를 확인하므로 DOM 이벤트 없는 값 변경과 document-changed가 없는 문서 교체도 이전 좌표를 쓰지 않는다. 무효 결과에서는 새 검색만 수행한다. 본문 편집 뒤 새 검색은 이동한 실제 매치를 선택하고, 그 클릭으로 치환하거나 이력을 추가하지 않는다. 정상 치환은 기존 snapshot 편집 경로를 그대로 사용한다. 엔진·편집 라우터·저장·복구·인쇄 구현은 변경하지 않았다.

설치된 Mac Electron 44.3.0에서 합성 1쪽 HWP/HWPX 입력 각각 다섯 경우, 총 열 경우를 검증했다. 실제 DOM 버튼과 현재 WASM/InputHandler를 사용했다. stale 클릭 전후 두 형식 전체 직렬화, 본문·모든 화면/인쇄 SVG·dirty·이력을 확인했다. 본문 편집 뒤에는 의도한 새 매치 선택과 저장 커서를 별도로 확인했다. 세 검색 조건 사례의 대기 중 redo를 실제로 수행해 유지됨을 검사했다. 이후 새 매치만 치환하고 실제 undo/redo를 수행했다. 각 입력의 HWP/HWPX 저장과 재열기 스무 건은 실제 host IPC·파일시스템으로 진행했고, 저장 파일 해시·본문·모든 SVG·clean·이력 초기화를 확인했다.

처음 관찰한 redo HWP 바이트 차이는 새 데이터 결함이 아니었다. 수정 전과 후의 원본/치환/undo/redo 진단 결과가 정확히 같았다. HWP의 DocInfo 첫 DocumentProperties 레코드(tag 16, level 0, 26바이트)에서 저장 커서의 pos 필드(offset 22–25)만 달랐다. 예시에서는 바꾸기 후 자동 다음 찾기의 커서가 41, redo가 복원한 편집 커서가 27이었다. main.ts의 기존 onBeforeExport가 현재 커서를 저장하기 때문에 생기는 차이다. HWP의 나머지 모든 스트림·본문·서식 레코드, HWPX 모든 항목과 ZIP 메타데이터는 같았다.

최종 저장 커서 90개를 실제 UI 커서·getStoredCaret·DocumentProperties 원시 값과 대조했다. undo/redo와 본문 편집 뒤 새 검색 22쌍을 모든 스트림·레코드·ZIP 항목으로 비교했다. 커서를 0으로 저장하는 동기 QA export에서 HWP/HWPX 파일 전체 바이트도 같았다. 비교에서 특정 바이트를 마스킹하거나 본문·서식 필드를 제외하지 않았다. QA export 뒤에는 기존 hook과 실제 저장 커서를 복원했고 UI 선택·커서·이력을 움직이지 않았다. 실제 생산 export와 그 저장 커서는 별도로 남겼다. 비교 도구는 `scripts/compare-find-document-serializers.py`이다.

원래 입력 형식으로 저장·재열기한 열 건은 해당 형식의 전체 바이트가 같았다. 변환 저장 열 건은 예상 본문·모든 SVG를 독립 비교하고, 변경하지 않은 core parser의 재열기 결과와 두 형식 전체 바이트를 비교했다. 이는 모든 변환 메타데이터의 무손실 보존을 의미하지 않는다. HWP→HWPX는 HWP 전용 summary·preview·기타 메타데이터 차이가 있고, HWPX→HWP를 다시 열면 PrvText가 본문으로 갱신된다. 해당 HWP를 HWPX로 다시 내보낼 때 기본 번호 서식의 autoIndent/useInstWidth도 달랐다. 수정 전 실제 앱의 HWPX를 같은 엔진으로 변환·재열기하면 수정 후 두 형식과 정확히 같은 바이트가 나온다는 별도 증거를 남겼다. 이 기존 형식 변환 한계는 이번 수정 범위에서 해결하지 않았다.

전체 desktop 83개 중 82개 통과·기존 complex-picture fixture 부재 1개 생략, 찾기 회귀 9개와 TypeScript noEmit 통과. 명령·exit·원본 TAP·stdout/stderr 해시와 검사 전후 소스 80개 manifest를 보존했다. 실제 실행 runtime 53개와 소스/runner 해시도 전후 일치한다. build는 기존 자산 13개를 재사용하고 바뀐 3개만 기록한 QA 런타임을 계속 하드링크로 재사용했다. 전체 패키징·엔진 빌드·외부 설치·Chrome 편집기 검증은 수행하지 않았다.

초기 QA에는 준비 완료·타이핑 그룹·저장 커서·새 검색 선택 이동·형식 변환을 잘못 가정한 실패와 Electron Preferences 임시 파일의 예산 스캔 경합이 있었다. 모두 실패로 표시하고 출력·문서·실행 소스를 보존했다. 예산 검사는 이 QA 프로필의 사라진 Preferences 임시 파일에만 전체 재스캔을 최대 세 번 하며, 다른 오류는 그대로 중단한다. 14개 실행은 모두 자체 앱이 정상 exit 0으로 종료됐고 강제 종료는 없었다. baseline 진단은 capture 범위이며 acceptance 통과로 합산하지 않았다. OS window.print는 차단됐고 실제 호출 시도는 0회였다. 파일 선택 결과만 합성 경로로 제어했다.

기존 dirty 파일 4개·잠금파일 3개·WASM, 이전 증거 273개·Swift 컴파일 캐시 133개를 보존했다. PR48 고정 head `e00a5060d34a20ca6eb5f3ba3ec5892fa9a7acc4`의 공개 검증 9개와 runtime 53개도 동일하다. 공개 문서 저장 전 보존 검사에서 전체 소유 경로는 4,772,098,048바이트로 7GiB 안에 있다. 정상/실패 증거는 각각 785,944,576 / 163,991,552바이트이며 미완료 phase는 없다. 공개 결과에는 합성 문서의 결과·해시·소스·검증 문서만 포함하고 원본 문서·앱·캐시는 포함하지 않는다.

복잡한 표·중첩 셀·여러 언어 검색어/IME, Linux, OS 인쇄 및 독립 PDF 끝 검색은 미검증이다. 다음 구현 후보는 이번에 분리한 HWPX↔HWP 번호 서식 autoIndent/useInstWidth의 보존이다. 실제 번호 문단에서 저장·재열기 배치 차이를 먼저 재현해 좁게 수정하는 것이 적절하다. 병합·릴리스는 별도 독립 검토 범위다.
